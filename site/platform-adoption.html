INTEGRATION INVARIANTS

Port the boundary, not the platform.

Prefer upstream Zephyr drivers. Keep OEM-specific policy outside the generic core. Never infer physical completion from a service response. Fail on missing mandatory capabilities. Preserve independent controller operation. Record actual board and dependency revisions, resource budgets and test results.

05 / GET WORKING

From source to a first
observed result.

Run the benign desktop indicator first. Then choose an exact target and integration owner. These commands are intended for development, not vehicle deployment.

1. Build the desktop reference

CMake 3.21+, C17 compiler and Ninja on Linux or MSVC on Windows.

git clone https://github.com/susmithmrm/ZARC.git
cd ZARC
cmake --preset desktop-linux
cmake --build --preset desktop-linux
ctest --preset desktop-linux

Windows: substitute desktop-windows for the preset. Use the independent controller/broker fixture to evaluate observed-state behavior.

Repository quick start ↗

2. Select the native target

From a compatible initialized Zephyr workspace, using the pinned v4.2.0 candidate baseline:

python /path/to/ZARC/tools/patch_uart_emulator.py /path/to/zephyr
west twister -T /path/to/ZARC/platform/zephyr \
  -p native_sim/native/64 --inline-logs

The expanded simulator lane, including four profile configurations and the independent worker, passed on 24466c77 after the documented emulator correction. Simulator results do not establish hardware support. Four candidate runtime profiles now have separate manifest and Twister configurations; see profile guide ↗.

Native setup ↗

3. Describe your composition

Copy the candidate target descriptor and adapt it to the selected board and profile. Resolve Kconfig, device ownership, required features and budgets before admission.

python tools/target_manifest.py \
  config/targets/native-sim-edge.json \
  --header build/generated/zarc_manifest.h
Example manifest ↗

4. Establish verification evidence

Run the trace check; prepare actual configuration-specific raw test evidence and obtain responsible approval. The structural check alone is not acceptance.

python tools/verify_evidence.py --trace-only
python tools/build_evidence.py --build build \
  --configuration desktop-lab \
  --out build-evidence.json
Evidence and HIL guide ↗

What happens during operation?

  1. DiscoverDiscover supported capabilities and establish a trusted session
  2. AdmitAdmit authorized, fresh typed intent within bounded resources
  3. ExecuteExecute local policy through native device ownership
  4. ObserveConfirm by independent observation and publish quality
  5. RecoverOn reset or loss, invalidate stale state and reconcile
